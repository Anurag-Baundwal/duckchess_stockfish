Quick reference
---------------
Build (PowerShell; MSYS2 g++ 15):
  $env:Path = "C:\msys64\ucrt64\bin;C:\msys64\usr\bin;" + $env:Path
  $env:TMP = <a writable folder>; $env:TEMP = $env:TMP
  cd src; make clean; make -j8 build ARCH=native COMP=mingw
  (ARCH=native resolves to x86-64-avxvnni on this laptop.)
Bench:   src/stockfish.exe bench   -> "Nodes searched" goes in the commit.
Format:  /c/msys64/clang64/bin/clang-format -i --style=file:.clang-format FILE
Git:     from Git Bash only (MSYS2's git ignores core.autocrlf).
Chess perft (Phase 1): python tests/chess_perft.py <absolute path to
  src\stockfish.exe>. tests/perft.sh itself needs `expect`, not installed.
wakwak (duck perft reference), with Rust 1.99 from rustup:
  set CARGO_TARGET_DIR to a folder outside the repo, then in repos7/wakwak
  `cargo build --release --locked` -> %CARGO_TARGET_DIR%\release\wakwak.exe
Duck perft: python tests/duck_perft_check.py <engine> [--wakwak <wakwak.exe>]
  [--max-depth N]; python tests/gen_duck_perft.py <wakwak.exe> recomputes the
  counts in tests/duck_perft.epd.
fastchess: clone github.com/Silverrzz/fastchess, check out cfa3671a44, run
  `make -j8` from PowerShell with MSYS2 on the Path. Duck games, e.g.
  fastchess.exe -variant duck960 -engine cmd=<abs path> name=a -engine
  cmd=<abs path> name=b -each tc=8+0.08 option.Hash=16 -openings
  file=<book.epd> format=epd order=random -rounds 50 -games 2 -repeat
  -concurrency 5 -pgnout file=<out.pgn>. Add -log file=<log> level=trace
  engine=true to see every engine line with timestamps.
Bench positions: python tests/gen_duck_bench.py <wakwak.exe> prints the
  list in src/benchmark.cpp, the same on every run (70 s).

2026-10-31  Analysis and decisions (before the repo existed)
  - Wrote ..\duck_engine_analysis.md. Main conclusions:
    * Fork Stockfish for its infrastructure (UCI, TT, threads, time
      management, bench, tune.h, Makefile/PGO), not for its search. Strip the
      search to a minimal baseline and bring features back one SPRT at a time,
      because many of Stockfish's tweaks assume ~35 moves per node (e.g.
      `r -= moveCount * 65` and the LMP move-count limit break at ~1000).
    * wakwak (5331 COPE, 8 weeks old) gets its strength from duck-specific
      pruning (duck refutations, Duck or Die, neutral ducks, caps per chess
      move and per duck square, duckless TT, duck-aware SEE) plus a large
      NNUE. Most of it is common sense; refutations and duckless hashing are
      the genuinely inventive parts.
    * A turn is one combined move (chess move + duck square), as in wakwak and
      Fairy-Stockfish. Split plies were rejected: Stockfish's stack assumes
      ss-1 is the opponent's move.
    * Testing: OpenBench needs a per-variant runner (port MattBench 213d671)
      with Silverrzz/fastchess `-variant duck`. That is a later, separate plan.
  - Reference perft: Fairy-Stockfish duck build
    repos7/Fairy-Stockfish/src/fsf-duck.exe (needs /c/msys64/clang64/bin on
    PATH for libc++.dll). Startpos perft 1 = 640, perft 2 = 379440.

2026-11-21  1.6  32-bit Move with a duck field, 2-entry TT         85d06fe3
  - Move is 32 bits: the low 16 keep Stockfish's layout and bits 16-21 hold
    the duck square (Move::duck_sq(), DuckSqShift = 16), always 0 for now.
    raw() returns all 32 bits. chess_raw() returns the low 16, which index
    the butterfly history, so it stays 2 x 65536 entries.
  - TT: an entry is 12 bytes (the 32-bit move after 2 bytes of padding), so
    a 32-byte cluster holds 2 entries next to the packed key word. The keys
    stay 21 bits each, in 42 of its 64 bits. A 16 MB table holds 1.05M
    entries instead of 1.57M. The TTEntry comment also lost its stale
    "key 16 bit" line.
  - The AVX-512 VBMI2 move generator (USE_AVX512ICL: Ice Lake and newer,
    Zen 4) writes 32-bit moves: 8 pawn moves with one 256-bit store, 32
    piece moves with two 512-bit stores. This laptop has no AVX-512, so that
    path and the AVX-512 move sorter are only compiled here
    (ARCH=x86-64-avx512icl and x86-64-avx512, no warnings). Check the bench
    on an AVX-512 machine before trusting them.
  - Speed: paired benches on two P-cores, 20 rounds: -0.39% +- 0.31% nps.
  - The bench grows 8%, all of it in position 37's qsearch (+2.2M nodes)
    with the smaller table. The other 48 positions differ by 74 nodes at
    most, and 36 of them are identical.
  - Verified: Bench 29784993 (two runs; also the debug build with

2026-11-21  2.3  Play duck chess                                   b0860998
  - The rules are PLAN.md's, as fastchess's DuckPosition and wakwak have
    them. There is no check: movegen lost pins, evasions and king safety
    (the king may step onto attacked squares, take the other king, and
    castle out of or through attack), and Position lost checkers, blockers,
    pinners, check squares, gives_check() and the cuckoo tables with
    upcoming_repetition().
  - Move generation still makes chess moves. Position::duck_targets(m)
    gives the squares the duck may then go to: the squares empty after the
    move, so including the one the piece left and the pawn taken en
    passant, but not its destination (for castling, the king's and the
    rook's destinations). The MovePicker and the root move list pair each
    chess move with every duck square, in square order, after the TT move.
    legal() checks both parts.
  - do_move() moves the duck after the piece and hashes it; undo_move()
    puts it back. A double push sets the en passant square only if an
    enemy pawn attacks it and the duck does not land on it.
  - Game end: a node whose side to move has no king returns
    mated_in(ply), one without a chess move mate_in(ply), a win. The
    fifty-move draw needs a chess move to exist; repetition is unchanged
    (the duck is in the key). qsearch always stands pat and searches
    captures, each with every duck square; its no-moves win check keeps
    upstream's stalemate condition (no pawn push, no piece but pawns).
  - The search has nothing duck-specific: no duck ordering and no qsearch
    duck cap. Any of that is Phase 6, one SPRT each.
  - UCI: moves read and write as "e2e4,e4d5", the chess move and then its
    destination with the duck square, as fastchess writes them; with
    UCI_Chess960, castling is "e1h1,h1b1". A king capture may come without
    the duck and then gets the first legal duck square. New combo option
    UCI_Variant (only "duck"), which fastchess sets.
  - Perft counts a game end below the root as one node, as wakwak does,
    and bulk-counts the duck squares at the last ply.
  - Bench: default depth 5 -> 3, 5.5 s. The chess move lists after four
    FENs went (they have no duck squares), and so did the two "changed
    threats" positions: position 37 did not finish depth 1 in 10 minutes,
    with every capture paired with every duck square in qsearch. Phase 3
    replaces the list.
  - Speed: startpos depth 4 in 11 ms, about 20M nps. On a 10+0.1 clock,
    move 1 took 1.6 s (depth 7): time management still overshoots.
  - Verified: Bench 111984881 (two runs; also the debug build with
    assertions and the NDK build on the tablet); clean build without
    warnings (the debug build adds upstream's -Wdangling-pointer for
    qsearch's pv); duck perft 242/242 (debug build 160/160 up to D2; the
    tablet matches perft 3 of two positions); Re1xe8 found as mate 1, and
    the duck on e4 stops it; a captured king gives bestmove (none); move
    lists with ducks parse, and a duck on the move's own destination is
    refused; Duck960 castling e1h1,h1b1; Threads 4 with MultiPV 2.
