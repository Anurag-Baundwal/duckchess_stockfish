Step 1: three terms, one branch and one SPRT each
-------------------------------------------------

All three off the same master, in src/evaluate.cpp: evaluate() (from the
side to move's view, like the duck shield) and a line in trace(), with the
constants next to DuckShield. Use Stockfish 11's form where it has the term
(repos6/Stockfish, tag sf_11, src/evaluate.cpp), as for RFP and mobility.

  1. eval-tempo: a bonus for the side to move, Stockfish 11's Tempo form,
     with wakwak's 30/25 cp converted.
  2. eval-pawn-defended: as in wakwak PR #87: per side, its pieces standing
     on squares its own pawns attack (pawn_attacks_bb), S(8, 6) cp each,
     converted. Stockfish 11 has no exact equivalent; write it in its style.
  3. eval-outposts: Stockfish 11's Outpost S(30, 21) (doubled for knights)
     and ReachableOutpost S(32, 10): relative ranks 4-6, supported by an
     own pawn, outside the enemy pawns' attack span. This contains wakwak's
     knight outpost (PR #86). There is no pawn hash, so compute the attack
     span directly.

For each branch:
  - clang-format (see AGENTS.md), then `stockfish.exe bench` for the commit's
    Bench line.
  - python tests/duck_perft_check.py must still pass (eval only).
  - `eval` on a FEN and on its colour-mirror: the new term must flip sign.
  - Commit message: what the term does for the engine, the credit
    ("as in wakwak (PR #87, +44 Elo there)" or the Stockfish 11 origin).
  - Push the branch to origin and create the OpenBench test: dev = branch,
    base = master, STC 10+0.1, Threads=1 Hash=16, SPRT [0, 3], confidence
    [0.20, 0.05], book Duck_DFRC.epd, priority 1.
  - Merge a pass with the "Passed STC" block (see git log for the format),
    and add the wakwak PR, if any, to the README's Acknowledgements list.


Step 2: tuning data (start right away; runs during step 1)
---------------------------------------------------------

No datagen yet (the user's decision), so the data is self-play games:

  - A local fastchess match, master vs master, at fixed nodes (about 20k
    per move), with -pgnout, on Duck_DFRC.epd (repos7/openbench/Client/

    fastchess-cfa3671a4488/fastchess.exe, with C:/msys64/ucrt64/bin first
    on PATH (it needs MSYS2's DLLs) and -variant duck960 (duck for
    standard starts). Time 100 games first, then size the run to a few
    hours, leaving cores for the laptop's OpenBench worker.
  - Plus the self-play games already in repos7/openbench/Client/PGNs, about
    5,150 from SPRT tests 186-197. Their comments hold each move's score
    and depth ({+0.64/5 0.104s}).
  - Never use games against wakwak or Fairy-Stockfish (tests 190, 199,
    200, 201, 202): their results are lopsided, and training on wakwak's
    games is the line the engine community cares about.


Step 3: texel tune (after step 1's SPRTs are decided)
----------------------------------------------------

Adapt the stockfish_4pc tools in repos7/hce-texel-tune (README.txt;
featfile.patch, linear_params.py, fit_linear.py, apply_linear.py) into a new
local folder, not committed:

  - PGN -> positions: skip book plies, game ends, mate scores and positions
    whose played move is a capture; remove duplicates; hold out 10%.
  - An engine command (patch, never committed) that writes the linear
    features of the current evaluation per position: piece-square counts mg
    and eg with the phase, tempo, defended pieces, outposts, the duck
    shield's danger squared.
  - Fit K first, then a logistic fit of all terms together. Target =
    0.5 * game result + 0.5 * sigmoid(search score from the PGN comment),
    as in the 4pc tune. Fit the tables in rank + file form first (one value
    per square overfits). Keep the piece values fixed: they also set the
    phase and SEE.
  - Apply the result as branch eval-texel and test it: STC vs master at
    priority 1, then an LTC (60+0.6, Hash 64).
  - Retune whenever terms are added later.


Later: search work (not yet; the user will say when)
---------------------------------------------------

What master's search has: PVS, TT, qsearch, reverse futility pruning in
Stockfish 11's form, the butterfly history, duck history, duck refutations
(also in qsearch), late duck pruning v2, Duck or Die, mate distance pruning,
and Stockfish's time management with the 2x-optimum cap.

What wakwak 0.10.0 already had that master doesn't (its SPRT Elo; summed
results overstate, and some won't transfer):
  - Neutral duck pruning (#94, #95): ducks that restrict none of the
    opponent's moves; keep the best one per chess move. +75, +14.
  - Duckless hashing (#66): a second TT probe with the duck left out of
    the key; use the stored move if it is legal here. +64.
  - Aspiration windows. +35.
  - Duck count pruning (#73, #75): cap chess moves searched per duck
    square. +27, +12.6.
  - IID (#85). +22. In Stockfish's form this is IIR.
  - Null-move reductions (#71, #84): reduce after a null-move fail-high.
    +4.8, +11.
  - Duck-stability time management (#104): more time while the chosen duck
    square keeps changing. +11.5.
  - LMR: plain PVS + LMR (#57) was only +11.5 there; then non-PV LMR
    (#102) and log-depth LMR (#108).
  - Continuation histories (#65, #67) and correction histories (#64,
    nonpawn).

Later wakwak additions (after 0.10.0): duck-aware SEE (#142, +66),
futility pruning (#113, +10.5), "exact" LMR (#114, +14.7), unique duck
pruning (#147, #151, #203), unique move pruning and LMR (#154, #155), quiet
duck history (#158), duck count history (#211), not penalising the best
move's duck or chess move (#107, #109, #110), scoring chess moves before
splitting ducks (#229, a speedup). Its repetition bug (#214: repetitions
judged on the duckless hash) is worth checking against our is_draw.

Stockfish features not in wakwak at all: cut-node tracking, ttPv,
cutoffCnt, doDeeper/doShallower, capture LMR, ProbCut, low-ply / TT-move
histories, effort-based time management. Analysis with details:
repos7/duck_engine_analysis.md, section 2.
